## What to build

A sender gets a dependable stored-message receipt through POST, delegated GET and the CLI, including after ambiguous network outcomes.

Implementation belongs in the msg service of `0000-chat/0000`. Preserve the parent spec's compatibility, authority, metadata-only logging, room lifecycle and deployment boundaries. Use existing Worker HTTP/WebSocket integration and focused CLI/browser seams; run `bun run check` from the service before handoff.

## Acceptance criteria

- [ ] Receipts consistently expose stored ID, sequence, timestamp and replay status.
- [ ] Same identifier/payload returns the original receipt; changed payload conflicts without a duplicate message.
- [ ] Preserve the separately authorized, disabled-by-default, revocable delegated GET capability and its request-id/rate/size constraints; do not grant management authority.
- [ ] Preserve compatibility of existing POST/CLI clients and keep secret capabilities out of receipts and logs.
- [ ] Verify public posting routes, retries and delegated capability disable/rotate against the real room integration seam.
