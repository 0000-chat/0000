## What to build

A participant can propose a structured request and the room owner can review and publish it through agent and browser flows.

Implementation belongs in the msg service of `0000-chat/0000`. Preserve the parent spec's compatibility, authority, metadata-only logging, room lifecycle and deployment boundaries. Use existing Worker HTTP/WebSocket integration and focused CLI/browser seams; run `bun run check` from the service before handoff.

## Acceptance criteria

- [ ] Requests have stable room-local IDs, source message references, purpose, owner label, requested output, unknowns, completion criteria and decision impact.
- [ ] Participant proposals remain visibly pending/reported; only management authority publishes canonical requests.
- [ ] Every proposal/publication records label, authority class, evidence, base revision and timestamp; retry identifiers prevent duplicate mutations and stale publication conflicts.
- [ ] Agent/CLI and browser users can propose, inspect evidence, publish and inspect published requests; empty state is explicit.
- [ ] Persistence uses the room boundary; quotas, rate limits, same-room references, deletion, cache validation and secret exclusion apply. No chat message or new-message notification is generated.
- [ ] Integration and client tests prove persistence across restart, authority separation, retries, revision conflicts and lifecycle limits.
