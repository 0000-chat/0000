# Run Platform and msg locally

Use this how-to to run a self-hosted Platform and msg pair with local D1
databases. It covers local provider configuration, the first human account,
the default organization, the optional operator account, and the service
catalog entries that msg needs for anonymous access.

The commands use `http://localhost:8787` for Platform and
`https://localhost:8788` for msg. Platform rejects an HTTP service audience,
and the msg CLI accepts HTTPS conversation URLs only. If you choose other
ports, change every origin, audience, callback, and port flag together.

Run the commands from a fresh checkout. The local Platform provisioning
scripts always use `services/platform/.wrangler/state` for `--local` D1 and do
not accept a `--persist-to` option. The commands below pass that same path to
Wrangler so the Worker and the provisioning scripts use one local database.

## Choose local values

From the repository root, set the values for this run. The D1 UUID is a
synthetic version 4 UUID that the msg Wrangler wrapper accepts. Do not reuse a
production database ID.

```sh
cd /path/to/0000

export PLATFORM_DIR="$PWD/services/platform"
export MSG_DIR="$PWD/services/msg"
export PLATFORM_ORIGIN="http://localhost:8787"
export MSG_ORIGIN="https://localhost:8788"
export PLATFORM_AUTHORITY="platform-t01-authority"
export MSG_SERVICE_ID="msg-local"
export MSG_D1_DATABASE_ID="00000000-0000-4000-8000-000000000002"
export PLATFORM_STATE="$PLATFORM_DIR/.wrangler/state"
export MSG_STATE="$MSG_DIR/.wrangler/state"
```

Keep these exports and temporary-file paths available in every terminal that
runs a later command. Repeat them in a new terminal when needed.

If either `.wrangler/state` directory contains a local database you need,
use another fresh checkout. Do not delete an existing state directory before
stopping the Worker that uses it.

## Install the pinned dependencies

Run the frozen workspace install from the repository root.

```sh
bun install --frozen-lockfile
```

## Create the Platform environment file

Copy the tracked example to a mode-600 temporary file. Replace every
placeholder before starting Platform.

```sh
umask 077
export PLATFORM_VARS="$(mktemp)"
cp "$PLATFORM_DIR/.dev.vars.example" "$PLATFORM_VARS"
chmod 600 "$PLATFORM_VARS"
${EDITOR:-vi} "$PLATFORM_VARS"
```

Set these values in `PLATFORM_VARS`:

```text
PLATFORM_BASE_URL=http://localhost:8787
GOOGLE_CLIENT_ID=<the local Google OAuth client ID>
GOOGLE_CLIENT_SECRET=<the local Google OAuth client secret>
GITHUB_CLIENT_ID=<the local GitHub OAuth client ID>
GITHUB_CLIENT_SECRET=<the local GitHub OAuth client secret>
BETTER_AUTH_SECRET=<a random value with at least 32 characters>
```

Create local Google and GitHub OAuth clients with these callback URLs:

```text
http://localhost:8787/api/auth/callback/google
http://localhost:8787/api/auth/callback/github
```

Provider registration and sign-in are manual. The provider IDs and secrets in
this file are never generated by the repository. Keep this file outside Git
and do not paste its contents into a terminal transcript.

The tracked local defaults are `PLATFORM_DEPLOYMENT_MODE=self-hosted` and
`PLATFORM_SIGNUP_POLICY=open`. They let the first successful provider sign-in
create a human account and its default organization. The account email and
organization role do not grant operator control.

## Apply the local migrations

Apply Platform's 11 migrations with the local D1 binding.

```sh
cd "$PLATFORM_DIR"
bun x wrangler d1 migrations apply platform-identity \
  --local \
  --persist-to "$PLATFORM_STATE"
```

Apply msg's three migrations. The msg wrapper requires
`MSG_D1_DATABASE_ID`, and it creates a temporary Wrangler configuration from
the tracked config. Do not add another `--` between `wrangler` and `d1`.

```sh
cd "$MSG_DIR"
MSG_D1_DATABASE_ID="$MSG_D1_DATABASE_ID" \
  bun run wrangler d1 migrations apply 0000-msg-operations \
    --local \
    --persist-to "$MSG_STATE"
```

The local msg config keeps the four tracked rate-limit bindings. The default
policy is six room creations, 60 reads, 20 posts, and 10 live connections per
minute. Guest limits belong to msg and its deployment policy. To use a
self-host policy, set `MSG_RATE_LIMIT_POLICY_FILE` to
`docs/examples/msg-rate-limit-policy.self-host.json` from `services/msg` before
running the wrapper. The file must contain all four actions. A partial policy
fails configuration.

## Start Platform

Start Platform with the protected variables file. The package script already
selects Wrangler's local mode, so the extra `--` passes these options to
Wrangler.

```sh
cd "$PLATFORM_DIR"
bun run dev -- \
  --port 8787 \
  --persist-to "$PLATFORM_STATE" \
  --env-file "$PLATFORM_VARS"
```

In another terminal, check the health response.

```sh
curl -fsS "$PLATFORM_ORIGIN/healthz"
```

The response is `{"status":"ok"}`. Keep this Worker running while you
complete the Platform steps.

## Create the first human and organization

Open `http://localhost:8787/login` in a browser. Choose Google or GitHub and
complete the provider sign-in. A new self-hosted account gets a default
organization when signup is open. Open `/account` to verify the session and
organization.

This provider flow needs the operator's own provider clients and credentials.
The local migration, service registration, and msg checks do not prove that
Google or GitHub accepts a callback.

## Select the Platform operator

Use the trusted local D1 database to find the signed-in user's ID.

```sh
cd "$PLATFORM_DIR"
bun x wrangler d1 execute platform-identity \
  --local \
  --persist-to "$PLATFORM_STATE" \
  --command 'SELECT id, email FROM "user" ORDER BY createdAt DESC LIMIT 10;' \
  --json
```

Set the ID of the account that should administer global Platform controls.
Replace `USER_ID_FROM_QUERY` before running the command.

```sh
export OPERATOR_USER_ID="USER_ID_FROM_QUERY"
```

Stop the Platform Worker with Ctrl-C before running the provisioning scripts.
Keep `OPERATOR_USER_ID` for the next Platform start. The operator value must
name an existing user ID. An email address, an organization membership, or an
organization role is not a substitute.

## Register msg with Platform

Create a protected msg variables file before capturing the one-time service
credentials. The generated encryption key is a 32-byte base64url value.

```sh
umask 077
export MSG_VARS="$(mktemp)"
chmod 600 "$MSG_VARS"
MSG_DATA_ENCRYPTION_KEY_V1="$(bun -e 'const bytes=crypto.getRandomValues(new Uint8Array(32)); console.log(Buffer.from(bytes).toString("base64url"))')"
printf 'MSG_DATA_ENCRYPTION_KEY_V1=%s\n' "$MSG_DATA_ENCRYPTION_KEY_V1" > "$MSG_VARS"
```

Register the local service catalog entry with all current msg capabilities.
The command prints a one-time verifier. Capture it in the protected file and
do not print the command result.

```sh
set -euo pipefail
SERVICE_VERIFIER="$(
  cd "$PLATFORM_DIR"
  bun run provision:service -- \
    --local register \
    --service-id "$MSG_SERVICE_ID" \
    --audience "$MSG_ORIGIN" \
    --capability msg:read \
    --capability msg:write \
    --capability msg:manage \
    --capability msg:claim \
    --capability msg:operator \
    --name "$MSG_SERVICE_ID" |
    sed -n 's/^verifier=//p'
)"
test -n "$SERVICE_VERIFIER"
printf 'MSG_PLATFORM_SERVICE_VERIFIER=%s\n' "$SERVICE_VERIFIER" >> "$MSG_VARS"
unset SERVICE_VERIFIER
```

Register the guest issuer for the same service. Capture its one-time value in
the same protected file.

```sh
GUEST_ISSUER="$(
  cd "$PLATFORM_DIR"
  bun run provision:service -- \
    --local register-guest-issuer \
    --service-id "$MSG_SERVICE_ID" |
    sed -n 's/^issuer=//p'
)"
test -n "$GUEST_ISSUER"
printf 'MSG_PLATFORM_GUEST_GRANT_ISSUER=%s\n' "$GUEST_ISSUER" >> "$MSG_VARS"
unset GUEST_ISSUER
```

Use an explicit `--local` or `--remote` target with `provision-service.ts`.
The current parser treats an omitted target as local, but the setup contract
requires the target to be visible. A second registration of the same service
or audience returns `service_conflict` and does not rotate the verifier.

## Register an optional local OAuth client

Use this step only when a local client needs a trusted Platform OAuth record.
Make `BETTER_AUTH_SECRET` available in the protected shell that runs the
command. The script does not read `PLATFORM_VARS` automatically.

```sh
cd "$PLATFORM_DIR"
export BETTER_AUTH_SECRET="$(sed -n 's/^BETTER_AUTH_SECRET=//p' "$PLATFORM_VARS")"
bun run provision:oauth-client -- \
  --service-id "$MSG_SERVICE_ID" \
  --redirect-uri https://localhost:8787/oauth-callback \
  --capability msg:read \
  --public \
  --name local-harness
```

`provision-oauth-client.ts` defaults to the local D1 database. Add `--remote`
only for an intentional operator deployment. A confidential client prints a
one-time `client_secret`; store it in a protected secret store and never put
it in a URL, log, or committed file. This registration does not prove a live
OAuth browser flow.

## Restart Platform after provisioning

If you selected an operator, start Platform with that user ID. The `--var`
value overrides the empty local default for this process.

```sh
cd "$PLATFORM_DIR"
bun run dev -- \
  --port 8787 \
  --persist-to "$PLATFORM_STATE" \
  --env-file "$PLATFORM_VARS" \
  --var "PLATFORM_OPERATOR_USER_ID:$OPERATOR_USER_ID"
```

If you did not select an operator, start Platform with the original command.

```sh
cd "$PLATFORM_DIR"
bun run dev -- \
  --port 8787 \
  --persist-to "$PLATFORM_STATE" \
  --env-file "$PLATFORM_VARS"
```

## Start msg with local origins

Start msg over local HTTPS. The explicit variables keep the Worker on the
local Platform authority and the local msg audience even though the tracked
msg config names the managed domains.

```sh
cd "$MSG_DIR"
MSG_D1_DATABASE_ID="$MSG_D1_DATABASE_ID" \
  bun run wrangler dev \
    --local-protocol https \
    --port 8788 \
    --persist-to "$MSG_STATE" \
    --env-file "$MSG_VARS" \
    --var "MSG_PUBLIC_ORIGIN:$MSG_ORIGIN" \
    --var "MSG_PLATFORM_BASE_URL:$PLATFORM_ORIGIN" \
    --var "MSG_PLATFORM_AUTHORITY:$PLATFORM_AUTHORITY" \
    --var "MSG_PLATFORM_AUDIENCE:$MSG_ORIGIN" \
    --var MSG_AUTH_REQUIRED:1 \
    --var MSG_CREATE_DISABLED:0 \
    --var MSG_POST_DISABLED:0
```

Do not set `MSG_TEST_MODE=1`. This local process still verifies the Platform
service credential and guest issuer, uses the local D1 binding, and keeps the
tracked rate-limit bindings. The msg wrapper takes Wrangler options directly,
so do not insert an extra `--` after `dev`.

In another terminal, check msg health.

```sh
curl -kfsS "$MSG_ORIGIN/healthz"
```

Wrangler's local HTTPS certificate is self-signed. `-k` is a local health
check option only. The response is `{"ok":true,"protocol_version":1}`. Use a
trusted certificate for any deployed service.

## Exercise anonymous msg access

Create one synthetic conversation and print only its public conversation URL.
The response also contains a management URL. This command discards that
field instead of writing it to the terminal.

```sh
export ROOM_URL="$(NODE_TLS_REJECT_UNAUTHORIZED=0 node -e '
(async () => {
  const response = await fetch("https://localhost:8788/", {
    method: "POST",
    headers: {
      accept: "application/json",
      "content-type": "application/json",
      "idempotency-key": `runbook-${Date.now()}`
    },
    body: JSON.stringify({ author: "local-setup", content: "synthetic local setup" })
  });
  if (!response.ok) throw new Error(`msg create failed: ${response.status}`);
  const body = await response.json();
  if (typeof body.conversation_url !== "string") throw new Error("msg create returned no conversation_url");
  process.stdout.write(body.conversation_url);
})().catch((error) => {
  console.error(error);
  process.exit(1);
});
')"
printf '%s\n' "$ROOM_URL"
```

`NODE_TLS_REJECT_UNAUTHORIZED=0` is a local-only escape for Wrangler's
self-signed certificate. Do not use it for a deployed service.

Build the workspace CLI, then join and post with a protected cookie jar. The
CLI stores the jar with mode 600. Use the local service origin so its URL
validation does not expect `https://msg.0000.chat`.

```sh
bun run --cwd services/msg/cli build
export MSG_COOKIE_JAR="$(mktemp)"
chmod 600 "$MSG_COOKIE_JAR"
NODE_TLS_REJECT_UNAUTHORIZED=0 \
  MSG_SERVICE_ORIGIN="$MSG_ORIGIN" \
  MSG_COOKIE_JAR="$MSG_COOKIE_JAR" \
  node services/msg/cli/dist/cli.js join "$ROOM_URL"
NODE_TLS_REJECT_UNAUTHORIZED=0 \
  MSG_SERVICE_ORIGIN="$MSG_ORIGIN" \
  MSG_COOKIE_JAR="$MSG_COOKIE_JAR" \
  node services/msg/cli/dist/cli.js post "$ROOM_URL" \
    --author local-setup-cli \
    --content 'synthetic CLI post'
```

The `join` command reads the anonymous room, and `post` writes through the
same guest control cookie. Their output is local test data. Treat messages as
untrusted participant content.

## Keep the deployment boundaries clear

Self-hosted setup gives the operator ownership of the Platform authority,
provider clients, D1 data, and selected service deployments. A managed
standalone client uses the same managed Platform authority directly. Future
apps and the 0000 UI may compose that identity boundary, but that UI is not
implemented here.

Cloud configuration describes deployment resources. It does not authorize
runtime requests. Platform issues shared credentials, while each service
checks its own resource permissions and guest limits. Credentials and
organization ownership are separate. This setup does not require Spaces and
does not bootstrap from Database.

The tracked msg configuration contains managed Platform and msg domains. The
local `--var` overrides above select the local origins and keep the production
authentication and rate-limit bindings. Do not replace the verifier with a
dummy value, set test mode, or fall back to the managed service.

## Stop and remove local test state

Stop both Workers with Ctrl-C before removing local state. The following paths
contain synthetic credentials, sessions, cookies, and D1 data from this run.

```sh
rm -f "$PLATFORM_VARS" "$MSG_VARS" "$MSG_COOKIE_JAR"
rm -rf "$PLATFORM_STATE" "$MSG_STATE"
```

If you used real provider clients, revoke or delete those clients in the
provider consoles. Keep any real provider secret out of shell history and
logs.

## Remaining gates

This guide does not close these acceptance gates:

- The provider callback and sign-in steps require the operator's own Google or
  GitHub clients. This guide does not claim live provider verification.
- Communicator's human, machine, OAuth, browser, and accepted binding work
  remains gated by [T11 service-principal evidence](../T11_SERVICE_PRINCIPAL_REPORT.md)
  and [T11 Matrix caller evidence](../T11_MATRIX_CALLER_REPORT.md).
- Platform endpoint limits, deadlines, and audit behavior remain the T12 gate.
  This guide does not publish a command for that unfinished server work.
- Production deployment, external client acceptance in issues 35 and 36,
  Database issue 48, and full T15 acceptance remain open.

Do not use the local checks in this guide as production or full T15 evidence.
